# 検知の実証テスト（PoC）

「CyberNote は本当に脆弱性を見つけられるのか」を、感想ではなく**数字**で示すための仕組みです。
営業資料・社内説明・不具合の切り分けに、そのまま使えます。

実証は2段構えです。**どちらか片方だけでは足りません。**

| | 何を確かめるか | どこで実行するか |
|---|---|---|
| ① 精度編（オフライン） | 判定ロジックが正しいか | 手元・CI（通信不要） |
| ② 実データ編 | 本物の脆弱性DBを正しく読めているか | cybernote.click の管理画面 |

---

## ① 精度編 — 判定ロジックの正しさ

```
php backend/tests/poc-detection.php
```

擬似データを使い、通信なしで実行します。所要1秒未満。

### 何を試しているか

1. **見逃さないか** … 影響のあるバージョンを、影響ありと判定できるか
2. **誤検知しないか** … 更新済みのサイトを「危険」と言わないか
3. **分からないときに黙るか** … 判断材料が無いのに脅かさないか
4. **表示が正しいか** … 修正版・CVE番号・深刻度・日本語説明が正しく出るか
5. **応答が壊れたとき** … 「確認できていない」を「安全」と混同しないか
6. **時間切れへの備え** … 最重要のWordPress本体を落とさないか
7. **相互検証** … 別実装で同じ判定をやり直しても同じ結論になるか
8. **対照実験** … 壊れた検知器（何も返さない／全部返す）をこの試験は見抜けるか
9. **変異テスト** … 判定ロジックをわざと11通り壊し、何割を検出できるか

### 現在の結果

```
判定ケース   73 件 → 正解 73 件（100.0%）
見逃し        0 件
誤検知        0 件
相互検証   1080 通り中 0 件が不一致
変異検出率  100.0%（11/11）
```

### この試験を作ったときに見つかった不具合

作る前のエンジン（コミット済みの版）に同じ試験をかけると、こうなります。

```
                     修正前          修正後
正解              48/73（65.8%）  73/73（100%）
見逃し                 10 件           0 件
誤検知                  9 件           0 件
相互検証の不一致  240/1080 通り    0/1080 通り
```

つまりこのPoCは、飾りではなく実際に8種類の欠陥を見つけています。

| 見つかった問題 | 起きること |
|---|---|
| 解釈できない下限表記が上限として扱われていた | 危険なサイトを「安全」と表示（**見逃し**） |
| `1.0` と `1.0.0` が別物として比較されていた | 更新済みなのに「危険」と表示（**誤検知**） |
| `6.0` と `6.0.0` が一致せず完全一致指定を取り落とす | **見逃し** |
| `v1.2.3` のような表記が最小値として扱われる | 最新版なのに「危険」と表示（**誤検知**） |
| 上限が空文字だと未修正の脆弱性を落としていた | 修正版が無い深刻な問題を**見逃し** |
| `lte` `gte` `<=` `>=` を解釈できなかった | DB側の表記が変わると全滅 |
| `"unfixed": "false"` を「未修正」と誤読 | 全利用者に誤った警告 |
| 影響範囲が配列で並ぶ形式を丸ごと無視 | その項目を全件**見逃し** |

あわせて、次も直しています。

- WordPress本体を**最初に**照合するようにした（時間切れで最重要項目が落ちないように）
- 1回の問い合わせ時間を残り時間に合わせて縮め、接続プラグイン側の60秒を超えないようにした
- `trunk` `latest` のような比較できない表記は判定不能として扱う（誤検知の防止）
- 応答の形が想定と違うときに「0件＝安全」と読まないようにした
- 同じ脆弱性が二重に表示されないようにまとめた
- 「確認できなかった件数」を記録するようにした（後述）

## ② 実データ編 — 本物のデータベース相手の実証

**設定 > CyberNote API** → 「**検知の実証テスト**」→「実証テストを実行」

初回は30〜90秒ほどかかります。2回目以降はキャッシュが効くため短時間で終わります。

### 出てくる数字の読み方

**① 脆弱性データベースの応答**
こちらの読み取り方が相手の仕様と合っているかを、推測ではなく実物で確認します。
「こちらが解釈できない表記」が**なし**であることが重要です。ここに何か出たら、
その表記に対応するまで取りこぼしが発生します。

**② 実データでの突合結果**
データベースが公開している影響範囲から「範囲の内側」と「範囲の外側（更新済み）」の
バージョンを機械的に作り、実際にスキャンしています。

- **範囲内で検知** … ✓ が並べば、危険なバージョンを見逃していません
- **更新後は沈黙** … ✓ が並べば、更新済みのサイトを脅かしていません

**③ 実サイト規模でのカバー率と速度**
日本の個人・小規模サイトを想定した構成で実測します。
**世界的な定番**と**日本向け**を分けて表示します。平均値だけだと弱点が隠れるためです。

日本向けの収録率が低く出た場合、それは製品の不具合ではなく
**脆弱性データベース側に情報が無い**ということです。ここが CyberNote が
独自に情報を足す価値のある部分になります。

**④ WordPress本体の扱い**
本体だけは「問い合わせたバージョン向けの結果が返る」前提で全件を採用しています。
「範囲情報あり」と「うち該当」が一致していれば、その前提は成り立っています。

## 大事な前提 — この実証で言えないこと

過大な期待を持たせないため、はっきり書いておきます。

**言えること**

- 脆弱性データベースに載っている情報を、正しく解釈して過不足なく伝えられている

**言えないこと**

- データベースに載っていない脆弱性まで見つけられる
- 未収録のプラグインが安全である
- データベースに書かれている影響範囲そのものが正しい

②の正解は「データベースが公開している影響範囲」から作っています。
したがって②が確かめているのは「渡された情報を正しく読めているか」であって、
「データベースの中身が正しいか」ではありません。
データベースの正しさまで検証したい場合は、開発元の変更履歴や NVD と
突き合わせる別の作業が必要になります。

## 「確認できなかった」を隠さない

脆弱性スキャナで一番まずいのは、**確認できていないものを「安全」と表示すること**です。
そこで次の件数を分けて記録しています（スキャン結果の `stats` に含まれます）。

| 項目 | 意味 |
|---|---|
| `components` | 実際に照合できた項目数 |
| `failed` | 通信できなかった項目数（→ 結果は「不完全」扱い） |
| `unknown` | 応答は返ったが形が違い、照合できなかった項目数 |
| `skipped` | バージョン表記が無く照合できなかった項目数（独自プラグイン等） |
| `unevaluated` | 影響範囲が書かれておらず判定を見送った脆弱性の件数 |

「0件見つかりました」と表示するときは、必ずこの数字とセットで見てください。

### 検討が必要な残りの論点

判断が割れるため、勝手に決めずに残してあります。実データ編の①で件数が出ます。

- **未修正なのに上限もある項目** … 現在は上限を優先し、上限より新しい版は報告していません。
  「修正版が無いのだから全バージョン影響では」という解釈もあり得ます。件数が多いようなら方針を決める必要があります。
- **`unknown` を「不完全」に含めるか** … 現在は含めていません。含めると、日本向けプラグインが
  未収録なだけで毎回「不完全」と表示され続けるためです。

## 開発時の使い方

コードを変えたら、この3つを通してから配布してください。

```
php backend/tests/run-tests.php        # 既存の動作確認
php backend/tests/poc-detection.php    # 検知精度（変異テスト込み）
php backend/tests/poc-selftest.php     # 実証テスト自体の自己検証
```

`poc-detection.php` は**変異検出率が100%を割ったら試験ケースの追加が必要**というサインです
（＝壊しても気づけない箇所がある）。実際、この仕組みを入れた直後に
「未知の下限表記」の壊れ方を検出できていないことが分かり、ケースを追加しています。

なお `/backend` は `.distignore` で配布対象から除外されているため、
これらのファイルが WordPress.org の配布ZIPに入ることはありません。
