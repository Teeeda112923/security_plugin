# カテゴリB 判定しきい値・表示文面 仕様書

無料版ハードニング設定診断の、各項目の三段階判定と日本語メッセージの定義

---

## 共通方針

- 三段階は good（問題なし）/ attention（改善が望ましい）/ recommended（早めの対処を推奨）。
- 各項目に「なぜ問題か」を一文、「どうすればよいか」を一手順だけ添える。
- 自動修正はしない。必要なら該当の設定画面へ案内するボタンを置く程度にとどめる。
- 既存サイトで変更するとリスクがある項目（ユーザー名・DB接頭辞）は、強く煽らず attention 止まりにする。新規構築時の推奨として伝える。
- 判定の読み取り対象は概念として示す。具体的な関数・定数・フックの実装は既存リポジトリの構造を確認しながら決定し、本書では確定しない。

---

## 1. 本番でのデバッグ表示（WP_DEBUG）

読み取る状態: デバッグ表示が有効か、エラーを画面に出す設定か。

- good: デバッグ表示が無効、またはエラーを画面に出さない設定
- attention: デバッグ自体は有効だがログのみで画面には出していない
- recommended: 本番でエラーが画面にそのまま表示される状態

> なぜ: エラー内容にサーバーの構成やファイルの場所が含まれ、訪問者や攻撃者に手がかりを与えます。
> どうする: 本番環境ではデバッグの画面表示をオフにしてください。

## 2. 管理画面からのファイル編集（DISALLOW_FILE_EDIT）

読み取る状態: 管理画面からテーマ・プラグインのコードを直接編集できるか。

- good: 編集が無効化されている
- recommended: 編集が有効なまま

> なぜ: 管理者アカウントが乗っ取られた場合、サイトのコードをその場で書き換えられてしまいます。
> どうする: 管理画面からのファイル編集を無効にする設定を追加してください。

## 3. 管理者ユーザー名が既定名か

読み取る状態: admin など推測されやすい名前の管理者が存在するか。

- good: 既定名の管理者が存在しない
- attention: admin / administrator などの既定名の管理者が存在する

> なぜ: 攻撃者が最初に試すのが既定の名前で、パスワードの総当たりの標的になりやすいです。
> どうする: 新しい名前の管理者を作って権限を移し、既定名のアカウントを削除してください。

注: ユーザー名は後からの変更に手間がかかるため、recommended までは上げず attention にとどめます。

## 4. 常時HTTPS（SSL）

読み取る状態: サイトのアドレスが https になっているか。

- good: https で配信されている
- recommended: http のまま

> なぜ: 通信が暗号化されず、ログイン情報などが途中で盗み見られる恐れがあります。
> どうする: SSL証明書を導入し、サイトを https に切り替えてください。多くのレンタルサーバーで無料の証明書が使えます。

## 5. データベースのテーブル接頭辞が既定値か

読み取る状態: 接頭辞が wp_ のままか。

- good: wp_ 以外に変更されている
- attention: wp_ のまま（既定値）

> なぜ: 既定値のままだと、一部の自動化された攻撃で狙いを定められやすくなります。
> どうする: 新しくサイトを作る際は別の接頭辞にしてください。すでに運用中のサイトは、変更にリスクがあるため無理に変えないでください。

注: 効果は限定的で、稼働中サイトでの変更は不具合の原因になりえます。診断は出しても弱い注意にとどめ、変更を急かしません。

## 6. XML-RPC の状態

読み取る状態: xmlrpc.php が有効か。

- good: 無効化されている
- attention: 有効になっている

> なぜ: 使っていない場合、総当たり攻撃やサイトを踏み台にした攻撃の入り口になることがあります。
> どうする: 外部連携アプリや一部の機能で使っていなければ、無効化を検討してください。使っている場合はそのままで問題ありません。

注: Jetpack や一部アプリ連携で必要な場合があるため、recommended には上げず、用途確認を促す表現にします。

## 7. REST API のユーザー名列挙

読み取る状態: 認証なしでユーザー名の一覧が取得できる状態か。

- good: ユーザー名の列挙が抑止されている
- attention: 外部からユーザー名を一覧取得できる

> なぜ: ログインに使う名前が外部から集められ、総当たり攻撃の準備に使われます。
> どうする: ユーザー名の列挙を無効化する設定を追加してください。

---

## 強さの一覧（設計の俯瞰）

| 項目 | 最も強い段階 | 理由 |
|---|---|---|
| デバッグ表示 | recommended | 攻撃の手がかりが直接漏れる |
| ファイル編集 | recommended | 乗っ取り時の被害が大きい |
| 常時HTTPS | recommended | 認証情報が平文で流れる |
| 管理者の既定名 | attention | 重要だが変更に手間、煽らない |
| XML-RPC | attention | 用途があり一律に危険ではない |
| DB接頭辞 | attention | 効果限定的、稼働中変更はリスク |
| ユーザー名列挙 | attention | 準備段階の対策、緊急度は中 |

recommended に置くのは「漏れる・壊される・盗まれる」の三つに絞り、残りは attention にしています。警告の強さを乱発しないことが、利用者の信頼と「煽らない」方針の両立につながります。

1. 各項目の読み取り方法を既存リポジトリの構造に合わせて確定する
2. 表示文面を管理画面UI用に最終調整し、翻訳ファイル（Text Domain: wp-security-checker）へ登録する
3. この7項目に既存のデバッグ診断を統合し、公式リポジトリ申請の最小構成として完成させる
