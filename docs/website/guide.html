Site Security Checkerの使い方（詳細ガイド）

WordPressのセキュリティを10項目で診断する無料プラグインです。専門知識ゼロで使え、診断はサイト内だけで完結するため外部へのデータ送信は一切ありません。このガイドではインストールから各項目の対処方法まで、すべてを丁寧に解説します。

インストール手順を見る よくある質問を見る

インストールから最初の診断まで

プラグインを有効化するだけで、すぐに診断が始まります。設定画面での初期設定は不要です。

  1. 手順1：プラグインをインストールする

    自動インストール（おすすめ）

    • WordPress管理画面の左メニューから 「プラグイン」→「新規追加」 を開きます
    • 右上の検索窓に 「Site Security Checker」 と入力します
    • 「今すぐインストール」ボタンをクリックします
    • インストールが完了したら 「有効化」 をクリックします

    ZIPからインストールする場合

    • WordPress.orgのプラグインページ からZIPファイルをダウンロードします
    • 管理画面の 「プラグイン」→「新規追加」→「プラグインのアップロード」 を開きます
    • ZIPファイルを選択して「今すぐインストール」をクリックします
    • 「有効化」をクリックします

  2. 手順2：診断結果を確認する

    有効化すると、2か所で診断結果を確認できます。

    ダッシュボードウィジェット（かんたん確認）
    管理画面のトップ（ダッシュボード）を開くと 「セキュリティ診断」ウィジェット が表示されます。確認が必要な件数が一目でわかり、「優先対応が必要な項目」がリストアップされます。

    専用管理画面（詳細確認）
    左メニューに 「セキュリティ診断」 という項目が追加されます。ここから全10項目の詳細な診断結果を確認できます。

  3. 手順3：再診断する

    ダッシュボードウィジェット右上の 「再診断」ボタン、または専用管理画面の 「再診断する」ボタン をクリックすると、ページを再読み込みせずに最新の状態を確認できます。設定を変更した後は、再診断ボタンで結果が更新されたことを確認してください。

診断結果の見方

診断結果は3段階のステータスで表示されます。それぞれの意味と優先度の考え方を確認してください。

🔴 要対応 — 今すぐ対応することをお勧めします

放置すると「ログイン情報が盗まれる」「サイトのファイルを書き換えられる」など、実害につながる可能性があります。表示された対処手順に従って、できるだけ早く対応してください。「要対応」と表示される項目は、セキュリティ上の影響が特に大きいもの（HTTPSを使っていない、管理画面からファイルを直接編集できる状態になっているなど）に限定しています。

🟡 改善推奨 — できれば対応を検討してください

すぐに被害が起きるわけではありませんが、攻撃の足がかりになりやすい設定です。他の対応が終わったあと、余裕があるときに確認してください。稼働中のサイトで変更にリスクを伴う項目（データベース接頭辞の変更など）は、この「改善推奨」以上には上げず、むやみに変更を急かしません。

✅ 問題なし — この項目は適切に設定されています

現時点では対応は不要です。定期的に再診断して、ステータスが変わっていないか確認することをお勧めします。

診断カードの見方

表示 内容
項目名何を診断しているか
現在の状態実際の設定値や検出結果
コメントなぜ問題か・何をすればよいか
›（詳細ボタン）対応手順・リスク・参考リンクを展開表示

優先順位の考え方：まず「要対応」をゼロにする → 次に「改善推奨」を減らす

「改善推奨」がすべて残っていても、「要対応」がゼロなら基本的なセキュリティレベルは確保できています。焦らず、一つずつ対応していきましょう。

カテゴリA：バージョン鮮度

WordPressを構成するソフトウェアが「最新の状態に保たれているか」を診断します。古いバージョンには既知の脆弱性（攻撃者が悪用できる弱点）が残ったままになることがあります。バージョンを最新に保つことは、セキュリティ対策の中でも特に効果が高い基本中の基本です。

A1. WordPress本体

あなたのサイトが使っているWordPressのバージョンが最新版かどうかを確認します。

ステータス 判定条件 対処の目安
✅ 問題なし 最新バージョンを使用中 対応不要
🟡 改善推奨 機能更新（新バージョン）が出ているが、セキュリティ修正ではない 余裕があるときに更新
🔴 要対応 セキュリティ修正を含むメンテナンス版（例: 6.7.1）が未適用 できるだけ早く更新する

「メンテナンス版」とは？
WordPressには「機能更新（例: 6.7→6.8）」と「セキュリティ修正（例: 6.7→6.7.1）」の2種類の更新があります。セキュリティ修正のほうが緊急度が高く、このプラグインでは「要対応」として強調表示します。

対処方法

  1. WordPress管理画面の 「ダッシュボード」→「更新」 を開きます
  2. 「WordPressの更新が利用可能です」と表示されていたら、「今すぐ更新」をクリックします
  3. 更新前にバックアップを取ることをお勧めします（多くのサーバーが自動バックアップ機能を提供しています）

参考：WordPress公式：アップデートの方法

A2. PHPバージョン

WordPressが動作しているサーバーの PHPバージョン を確認します。PHPはWordPressを動かすプログラム言語で、古いバージョンはセキュリティの修正を受け取れなくなります。

ステータス 判定条件 対処の目安
✅ 問題なし PHP 8.4 以上 対応不要
🟡 改善推奨 PHP 8.2 または 8.3（公式サポート中だが最新ではない） タイミングを見て更新
🔴 要対応 PHP 8.1 以下（公式サポート終了済みまたは間もなく終了） できるだけ早くバージョンアップ

「公式サポート終了」とは？
PHPの開発チームがバグやセキュリティの修正を提供しなくなった状態です。新しい脆弱性が発見されても修正されないため、使い続けるとリスクが高まります。

対処方法：PHPのバージョンはサーバーの管理画面から変更できます。

⚠️ 注意： PHPのバージョンを変えると、一部のプラグインやテーマが動かなくなることがあります。変更前に必ずバックアップを取り、できれば検証環境で確認してから本番に適用してください。

サーバー 変更場所の目安
さくらのレンタルサーバサーバーコントロールパネル →「PHP設定」
エックスサーバーサーバーパネル →「PHP Ver.切替」
ConoHa WINGコントロールパネル →「サイト管理」→「PHP設定」
ロリポップ！ユーザー管理ツール →「PHP設定」

参考：PHP公式：サポート中のバージョン一覧（英語）　／　WordPress公式：PHPについて

A3. プラグイン・テーマの更新

インストール済みのプラグインやテーマに 未適用の更新 があるかどうかを確認します。更新を放置すると、既知の脆弱性を抱えたまま運用を続けることになります。

ステータス 判定条件 対処の目安
✅ 問題なし 更新待ちのプラグイン・テーマが0件 対応不要
🟡 改善推奨 1件以上の更新が待機中 更新画面から適用する

WordPressのプラグインやテーマへの攻撃のほとんどは、すでに修正済みの脆弱性を狙ったものです。更新を適用するだけで、これらの攻撃の大半を防ぐことができます。

対処方法：診断カードの 「更新画面を開く」ボタン をクリックすると、WordPressの更新ページへ直接移動できます。

  1. 「更新画面を開く」をクリックします
  2. 更新したいプラグイン・テーマにチェックを入れます
  3. 「プラグインを更新」ボタンをクリックします

⚠️ 注意： プラグインの更新で画面が崩れたり機能が変わることがあります。本番サイトへの適用前に、バックアップを取ることをお勧めします。このプラグイン自体は更新を自動で実行しません。

参考：WordPress公式：プラグインの更新方法

カテゴリB：ハードニング設定

「ハードニング（Hardening）」とは、設定を見直してサイトを攻撃に強くすることを指します。カテゴリBではWordPressの7つの設定項目を診断します。バージョンの更新（カテゴリA）と合わせて対応することで、サイトのセキュリティレベルを大きく高めることができます。

B1. デバッグ表示

WordPressの デバッグ設定 が本番サイトで有効になっていないかを確認します。デバッグとはエラーの内容を表示する開発者向けの機能です。

ステータス 判定条件 対処の目安
✅ 問題なし WP_DEBUG がオフ 対応不要
🟡 改善推奨 WP_DEBUG がオンだが、画面表示はオフ（ログファイルのみ） 本番では完全にオフにすることが理想
🔴 要対応 WP_DEBUG がオンで、エラーが画面に表示される状態 すぐに無効化する

本番サイトでエラーを画面に表示すると、サーバーのフォルダ構成やファイルパスなど、攻撃者にとって有益な情報が漏れることがあります。

対処方法：wp-config.php（WordPressのルートフォルダにある設定ファイル）をテキストエディタで開き、以下の行を探して変更します。

変更前（問題のある状態）

define( 'WP_DEBUG', true );
define( 'WP_DEBUG_DISPLAY', true );

変更後（安全な状態）

define( 'WP_DEBUG', false );

wp-config.php はサーバーのFTPやファイルマネージャー経由で編集できます。変更前にファイルのバックアップを取ってください。

参考：WordPress公式：デバッグの設定（英語）

B2. ファイル編集機能

WordPress管理画面から、プラグインやテーマのファイルを直接編集できる状態になっていないかを確認します。

ステータス 判定条件 対処の目安
✅ 問題なし DISALLOW_FILE_EDIT が true に設定されている 対応不要
🔴 要対応 設定が未定義、または false（編集可能な状態） すぐに無効化する

管理者アカウントが乗っ取られた場合、攻撃者は管理画面のエディターから悪意のあるコード（マルウェア）をテーマやプラグインに直接書き込むことができます。この機能を無効化することで、万が一ログインされても被害を最小限に抑えられます。

対処方法：wp-config.php に以下の1行を追加します。

define( 'DISALLOW_FILE_EDIT', true );

追加する場所は /* That's all, stop editing! */ という行のすぐ上が一般的です。追加後、管理画面の 「外観」→「テーマファイルエディター」 と 「プラグイン」→「プラグインファイルエディター」 のメニューが消えれば設定完了です。

参考：WordPress公式：wp-config.phpについて（英語）

B3. 管理者ユーザー名

admin、administrator などの 推測されやすいユーザー名 を持つ管理者アカウントが存在しないかを確認します。

ステータス 判定条件 対処の目安
✅ 問題なし 推測されやすいユーザー名を持つ管理者が存在しない 対応不要
🟡 改善推奨 admin、administrator などのアカウントが存在する 余裕があるときに変更を検討

パスワードを総当たりで試すブルートフォース攻撃では、ユーザー名に admin が使われることが非常に多いです。ユーザー名を推測しにくい名前にするだけで、攻撃の成功率を下げることができます。

対処方法：WordPressでは作成済みのユーザー名は変更できません。代わりに以下の手順で対処します。

  1. 管理画面の 「ユーザー」→「新規ユーザーを追加」 から、新しい任意のユーザー名で管理者アカウントを作成します
  2. 新しいアカウントでログインし直します
  3. 古い admin アカウントを削除します（削除時に既存の投稿を新しいアカウントへ引き継ぐよう選択できます）

⚠️ 注意： 誤って自分が使っているアカウントを削除しないよう注意してください。必ず新しいアカウントでログインできることを確認してから古いアカウントを削除してください。

B4. 常時HTTPS

サイトが HTTPS（SSL） で運営されているかを確認します。

ステータス 判定条件 対処の目安
✅ 問題なし サイトのURLが https:// で始まっている 対応不要
🔴 要対応 サイトのURLが http:// のまま（暗号化されていない） SSL証明書を設定する

HTTPのままだと、ログインするときのパスワードや、フォームに入力した内容が 暗号化されずに通信 されます。同じWi-Fiを使っている人に傍受される可能性があります。

対処方法：ほとんどのレンタルサーバーでは、無料のSSL証明書を提供しています。

  1. レンタルサーバーの管理画面で「SSL」「HTTPS」のメニューを探します
  2. 無料SSL（Let's Encrypt など）を有効にします
  3. WordPress管理画面の 「設定」→「一般」 を開き、「WordPressアドレス」と「サイトアドレス」のURLを https:// に変更します

すでにSSL証明書が設定されているのに「要対応」と表示される場合は、サイトのURLが http:// のままになっている可能性があります。「設定」→「一般」でURLをご確認ください。

B5. データベース接頭辞

WordPressが使うデータベースのテーブル名に付く 接頭辞（プレフィックス） が、デフォルト値の wp_ のままになっていないかを確認します。

ステータス 判定条件 対処の目安
✅ 問題なし 接頭辞が wp_ 以外に変更されている 対応不要
🟡 改善推奨 接頭辞が wp_（デフォルト値のまま） 新規構築時は変更推奨。稼働中は無理に変更しない

wp_ のままだと、SQLインジェクション攻撃などの際にテーブル名を推測されやすくなります。ただし、それだけで直接攻撃が成立するわけではなく、影響度は限定的です。

⚠️ 稼働中のサイトでの変更は推奨しません。
データベース接頭辞の変更は、設定ファイルとデータベースの両方を正確に書き換える必要があり、手順を誤るとサイトが完全に壊れる可能性があります。新しくサイトを構築する場合のみ、インストール時に wp_ 以外の接頭辞（例: mysite_）を指定してください。稼働中のサイトの場合は、他の項目を優先してください。

B6. XML-RPC

WordPressの XML-RPC 機能が有効になっているかを確認します。XML-RPCは外部アプリからWordPressを操作するための古い仕組みです。

ステータス 判定条件 対処の目安
✅ 問題なし XML-RPCが無効化されている 対応不要
🟡 改善推奨 XML-RPCが有効（xmlrpc.php が利用可能） 使っていなければ無効化を検討

XML-RPCはブルートフォース攻撃の入り口として悪用されることがあります。ただし、Jetpackプラグイン・WordPressスマートフォンアプリ・外部からWordPressを操作するツールを使っている場合は無効化すると動かなくなります。使っていない場合に限り、無効化を検討してください。

方法1：プラグインで無効化する（かんたん）
「Disable XML-RPC」などのプラグインをインストールして有効化するだけで無効化できます。

方法2：.htaccess に追記する（上級者向け）
WordPressのルートにある .htaccess ファイルに以下を追加します。

<Files xmlrpc.php>
  Order deny,allow
  Deny from all
</Files>

参考：WordPress公式：XML-RPCについて（英語）

B7. REST APIユーザー名列挙

WordPressのREST APIを通じて、ログインユーザー名が外部から取得できる状態になっていないかを確認します。具体的には /wp-json/wp/v2/users というURLに、ログインなしでアクセスしたときにユーザー情報が返ってくるかを診断します。

ステータス 判定条件 対処の目安
✅ 問題なし 匿名アクセスでユーザー情報が取得できない 対応不要
🟡 改善推奨 匿名で /wp/v2/users からユーザー情報が取得できる functions.phpにコードを追加して制限する

ログインに使うユーザー名が外部から丸見えになっていると、あとはパスワードを総当たりするだけになります（B3の問題と組み合わさると特に危険です）。

対処方法：functions.php（使用中のテーマフォルダにある設定ファイル）または子テーマの functions.php に以下を追加します。

add_filter( 'rest_endpoints', function( $endpoints ) {
    if ( isset( $endpoints['/wp/v2/users'] ) ) {
        foreach ( $endpoints['/wp/v2/users'] as $key => $endpoint ) {
            if ( empty( $endpoint['permission_callback'] ) ) {
                $endpoints['/wp/v2/users'][ $key ]['permission_callback'] = function() {
                    return current_user_can( 'list_users' );
                };
            }
        }
    }
    return $endpoints;
} );

テーマの functions.php を直接編集するのが不安な場合は、「Code Snippets」などのプラグインを使ってコードを追加する方法もあります。

参考：WordPress公式：REST API ユーザーエンドポイント（英語）

よくある質問

無料で使えますか？

はい、無料でお使いいただけます。現在公開している全10項目の診断機能はすべて無料です。将来的にプラグインやテーマの脆弱性（CVE）を日本語でお知らせするPro版を予定していますが、現在の診断機能は無料のまま提供し続けます。

WordPressのバージョンはいくつから使えますか？

WordPress 5.9 以上、PHP 7.4 以上が必要です。WordPress 6.x 系をお使いの方は問題なくご利用いただけます。

有効化したらすぐに使えますか？

はい。有効化した直後から、管理画面のダッシュボードに診断ウィジェットが表示されます。設定画面で何かを入力したり、初期設定をしたりする必要はありません。

マルチサイト環境でも使えますか？

現時点では単一サイト向けの設計です。マルチサイト環境での動作は確認していません。

診断はいつ実行されますか？

管理画面のダッシュボードまたは専用管理画面を開いたときに実行されます。常時バックグラウンドで動き続ける処理はありません。「再診断」ボタンを押すと、その場で最新の状態を確認できます。

設定を変更したのに結果が変わりません

「再診断」ボタンを押してください。診断は自動では更新されません。設定を変更したあとは「再診断する」ボタン（専用管理画面の右上）または「再診断」ボタン（ダッシュボードウィジェット右上）をクリックしてください。

「改善推奨」の項目を全部直さないといけませんか？

いいえ、必須ではありません。まず「要対応」をゼロにすることを優先してください。「改善推奨」はリスクを下げるための推奨事項ですが、すぐに被害につながるわけではありません。「要対応」がゼロの状態を保ちながら、余裕があるときに「改善推奨」に取り組んでいただければ十分です。

XML-RPCを無効化すると何かが壊れますか？

Jetpackや一部のスマートフォンアプリを使っている場合は動かなくなります。以下のサービス・機能を使っている場合、無効化しないでください。

  • Jetpackプラグイン
  • WordPressの公式スマートフォンアプリ（iOS / Android）
  • 外部のブログ投稿ツール（Windows Live Writer など）

これらを使っていない場合は、無効化しても問題ありません。

REST APIのユーザー列挙を無効化すると何か影響がありますか？

一部のプラグインが著者アーカイブページや投稿者情報を取得できなくなる場合があります。ほとんどの一般的なWordPressサイトでは問題ありません。無効化後に問題が発生した場合は、追加したコードを削除して元に戻してください。

外部のサーバーにデータを送っていますか？

一切送っていません。すべての診断はあなたのサーバー内だけで完結します。プラグインが外部のサーバーへ通信することはありません（APIキーも不要です）。

このプラグインはサイトの設定を自動で変更しますか？

しません。Site Security Checker は診断と情報提供に特化しています。設定の変更や更新の実行は、すべて利用者ご自身に委ねています。

プラグインを削除するとサイトに何か残りますか？
