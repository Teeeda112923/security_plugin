# カテゴリB：ハードニング設定

「ハードニング（Hardening）」とは、設定を見直してサイトを攻撃に強くすることを指します。カテゴリBでは、WordPressの7つの設定項目を診断します。

バージョンの更新（カテゴリA）と合わせて対応することで、サイトのセキュリティレベルを大きく高めることができます。

---

## B1. デバッグ表示

### 何を診断しますか？

WordPressの **デバッグ設定** が本番サイトで有効になっていないかを確認します。デバッグとはエラーの内容を表示する開発者向けの機能です。

### ステータスの判定基準

| ステータス | 条件 |
|---|---|
| ✅ 問題なし | `WP_DEBUG` がオフ |
| 🟡 改善推奨 | `WP_DEBUG` がオンだが、画面表示はオフ（ログファイルのみ） |
| 🔴 要対応 | `WP_DEBUG` がオンで、エラーが画面に表示される状態 |

### なぜ問題なのですか？

本番サイトでエラーを画面に表示すると、サーバーのフォルダ構成やファイルパスなど、攻撃者にとって有益な情報が漏れることがあります。

### 対処方法

`wp-config.php`（WordPressのルートフォルダにある設定ファイル）をテキストエディタで開き、以下の行を探して変更します。

**変更前（問題のある状態）**
```php
define( 'WP_DEBUG', true );
define( 'WP_DEBUG_DISPLAY', true );
```

**変更後（安全な状態）**
```php
define( 'WP_DEBUG', false );
```

> `wp-config.php` はサーバーのFTPやファイルマネージャー経由で編集できます。変更前にファイルのバックアップを取ってください。

### 参考

- [WordPress公式：デバッグの設定（英語）](https://wordpress.org/documentation/article/debugging-in-wordpress/)

## B2. ファイル編集機能

### 何を診断しますか？

WordPress管理画面から、プラグインやテーマのファイルを直接編集できる状態になっていないかを確認します。

### ステータスの判定基準

| ステータス | 条件 |
|---|---|
| ✅ 問題なし | `DISALLOW_FILE_EDIT` が `true` に設定されている |
| 🔴 要対応 | 設定が未定義、または `false`（編集可能な状態） |

### なぜ問題なのですか？

管理者アカウントが乗っ取られた場合、攻撃者は管理画面のエディターから悪意のあるコード（マルウェア）をテーマやプラグインに直接書き込むことができます。この機能を無効化することで、万が一ログインされても被害を最小限に抑えられます。

### 対処方法

`wp-config.php` に以下の1行を追加します。

```php
define( 'DISALLOW_FILE_EDIT', true );
```

> 追加する場所は `/* That's all, stop editing! */` という行のすぐ上が一般的です。

追加後、管理画面の **「外観」→「テーマファイルエディター」** と **「プラグイン」→「プラグインファイルエディター」** のメニューが消えれば設定完了です。

### 参考

- [WordPress公式：wp-config.phpについて（英語）](https://developer.wordpress.org/apis/wp-config-php/)

## B3. 管理者ユーザー名

### 何を診断しますか？

`admin`、`administrator` などの **推測されやすいユーザー名** を持つ管理者アカウントが存在しないかを確認します。

### ステータスの判定基準

| ステータス | 条件 |
|---|---|
| ✅ 問題なし | 推測されやすいユーザー名を持つ管理者が存在しない |
| 🟡 改善推奨 | `admin`、`administrator` などのアカウントが存在する |

### なぜ問題なのですか？

パスワードを総当たりで試すブルートフォース攻撃では、ユーザー名に `admin` が使われることが非常に多いです。ユーザー名を推測しにくい名前にするだけで、攻撃の成功率を下げることができます。

### 対処方法

WordPressでは **作成済みのユーザー名は変更できません**。代わりに以下の手順で対処します。

1. 管理画面の **「ユーザー」→「新規ユーザーを追加」** から、新しい任意のユーザー名で管理者アカウントを作成します
2. 新しいアカウントでログインし直します
3. 古い `admin` アカウントを削除します（削除時に既存の投稿を新しいアカウントへ引き継ぐよう選択できます）

> **注意：** 誤って自分が使っているアカウントを削除しないよう注意してください。必ず新しいアカウントでログインできることを確認してから古いアカウントを削除してください。

## B4. 常時HTTPS

### 何を診断しますか？

サイトが **HTTPS（SSL）** で運営されているかを確認します。

### ステータスの判定基準

| ステータス | 条件 |
|---|---|
| ✅ 問題なし | サイトのURLが `https://` で始まっている |
| 🔴 要対応 | サイトのURLが `http://` のまま（暗号化されていない） |

### なぜ問題なのですか？

HTTPのままだと、ログインするときのパスワードや、フォームに入力した内容が **暗号化されずに通信** されます。同じWi-Fiを使っている人に傍受される可能性があります。

### 対処方法

ほとんどのレンタルサーバーでは、**無料のSSL証明書** を提供しています。

1. レンタルサーバーの管理画面で「SSL」「HTTPS」のメニューを探します
2. 無料SSL（Let's Encrypt など）を有効にします
3. WordPress管理画面の **「設定」→「一般」** を開き、「WordPressアドレス」と「サイトアドレス」のURLを `https://` に変更します

> すでにSSL証明書が設定されているのに「要対応」と表示される場合は、サイトのURLが `http://` のままになっている可能性があります。「設定」→「一般」でURLをご確認ください。

## B5. データベース接頭辞

### 何を診断しますか？

WordPressが使うデータベースのテーブル名に付く **接頭辞（プレフィックス）** が、デフォルト値の `wp_` のままになっていないかを確認します。

### ステータスの判定基準

| ステータス | 条件 |
|---|---|
| ✅ 問題なし | 接頭辞が `wp_` 以外に変更されている |
| 🟡 改善推奨 | 接頭辞が `wp_`（デフォルト値のまま） |

### なぜ問題なのですか？

`wp_` のままだと、SQLインジェクション攻撃などの際にテーブル名を推測されやすくなります。ただし、それだけで直接攻撃が成立するわけではなく、影響度は限定的です。

### 対処方法

> **⚠️ 稼働中のサイトでの変更は推奨しません。**  
> データベース接頭辞の変更は、設定ファイルとデータベースの両方を正確に書き換える必要があり、手順を誤るとサイトが完全に壊れる可能性があります。

**新しくサイトを構築する場合：** インストール時に `wp_` 以外の接頭辞（例: `mysite_`）を指定してください。

**稼働中のサイトの場合：** 無理に変更しないことをお勧めします。他の項目を優先してください。

## B6. XML-RPC

### 何を診断しますか？

WordPress の **XML-RPC** 機能が有効になっているかを確認します。XML-RPCは外部アプリからWordPressを操作するための古い仕組みです。

### ステータスの判定基準

| ステータス | 条件 |
|---|---|
| ✅ 問題なし | XML-RPCが無効化されている |
| 🟡 改善推奨 | XML-RPCが有効（`xmlrpc.php` が利用可能） |

### なぜ問題になることがありますか？

XML-RPCはブルートフォース攻撃の入り口として悪用されることがあります。ただし、**以下のサービスを使っている場合は無効化すると動かなくなります：**

- Jetpackプラグイン
- WordPressスマートフォンアプリ（iOS/Android）
- 外部からWordPressを操作するツール全般

使っていない場合に限り、無効化を検討してください。

### 対処方法（使っていない場合）

**方法1：プラグインで無効化する（かんたん）**

「Disable XML-RPC」などのプラグインをインストールして有効化するだけで無効化できます。

**方法2：`.htaccess` に追記する（上級者向け）**

WordPressのルートにある `.htaccess` ファイルに以下を追加します。

```apache
<Files xmlrpc.php>
  Order deny,allow
  Deny from all
</Files>
```

### 参考

- [WordPress公式：XML-RPCについて（英語）](https://developer.wordpress.org/apis/xml-rpc/)

## B7. REST APIユーザー名列挙

### 何を診断しますか？

WordPress の REST API を通じて、**ログインユーザー名が外部から取得できる状態** になっていないかを確認します。

具体的には `/wp-json/wp/v2/users` というURLに、ログインなしでアクセスしたときにユーザー情報が返ってくるかを診断します。

### ステータスの判定基準

| ステータス | 条件 |
|---|---|
| ✅ 問題なし | 匿名アクセスでユーザー情報が取得できない |
| 🟡 改善推奨 | 匿名で `/wp/v2/users` からユーザー情報が取得できる |

### なぜ問題なのですか？

ログインに使うユーザー名が外部から丸見えになっていると、あとはパスワードを総当たりするだけになります（B3の問題と組み合わさると特に危険です）。

### 対処方法

`functions.php`（使用中のテーマフォルダにある設定ファイル）または子テーマの `functions.php` に以下を追加します。

```php
add_filter( 'rest_endpoints', function( $endpoints ) {
    if ( isset( $endpoints['/wp/v2/users'] ) ) {
        foreach ( $endpoints['/wp/v2/users'] as $key => $endpoint ) {
            if ( empty( $endpoint['permission_callback'] ) ) {
                $endpoints['/wp/v2/users'][ $key ]['permission_callback'] = function() {
                    return current_user_can( 'list_users' );
                };
            }
        }
    }
    return $endpoints;
} );
```

> テーマの `functions.php` を直接編集するのが不安な場合は、「Code Snippets」などのプラグインを使ってコードを追加する方法もあります。

### 参考

- [WordPress公式：REST API ユーザーエンドポイント（英語）](https://developer.wordpress.org/rest-api/reference/users/)
