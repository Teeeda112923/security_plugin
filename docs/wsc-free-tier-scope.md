# 無料版スコープ設計書

WP Security Checker 無料版で提供する診断項目と、Proとの線引きの定義

---

## 1. 無料版の役割（再確認）

無料版のゴールは収益ではなく、公式リポジトリでのインストール数とレビューという信頼資産を積むことです。そのため無料版は「入れてすぐ価値がわかる・サイトを壊さない・軽い」の三つを満たす必要があります。

役割を一文にすると、「サイトの設定を診断して、危険な状態を平易な日本語で気づかせる」ことに徹します。修正は自動で行わず、何をすべきかを提示するにとどめます。

---

## 2. 無料とProの線引き（最重要）

判定に必要なデータの所在で、機能の所属を決めます。これが設計全体の背骨になります。

| 判定に必要なもの | 所属 | 理由 |
|---|---|---|
| サイト内の設定・状態を読むだけで判定できる | 無料 | 外部通信不要、軽量、サイトを壊さない |
| 外部の脆弱性データベースとの突合が必要 | Pro | 価値の源泉、開発資産（CVEパイプライン）を要する |
| 定期実行・メール通知が必要 | Pro | 常駐処理・配信基盤が必要 |

具体例で言うと、「プラグインに更新が来ているか」はWordPress本体がすでに持っている更新情報を読むだけなので無料。「そのバージョンに既知のCVEがあるか」は外部DBとの突合が必要なのでPro。利用者から見ても「更新の有無は無料、危険度の判定は有料」という分かりやすい段差になります。

---

## 3. 無料版の診断項目（スコープ確定案）

すべて good / attention / recommended の三段階で表示します。外部通信は行わず、サイト内の設定・WordPress組み込み情報の読み取りだけで判定します。

### カテゴリA：バージョンの鮮度

| 項目 | 判定の考え方 |
|---|---|
| WordPress本体が最新か | WordPress組み込みの更新情報を読み取り、更新ありなら attention |
| PHPバージョンがサポート対象か | 閾値をプラグイン内に持ち、サポート切れ間近・切れで段階表示 |
| プラグイン・テーマの未更新件数 | 組み込みの更新情報から、更新待ち件数とプラグイン名を表示。「更新画面を開く」ボタンで、該当プラグインに絞り込んだWordPress標準の更新画面へ案内する。更新の実行はWordPressと利用者に委ね、プラグイン自身は更新を実行しない |

### カテゴリB：ハードニング設定

| 項目 | 判定の考え方 |
|---|---|
| 本番でのデバッグ表示（WP_DEBUG） | 既存実装。本番で有効なら recommended で警告 |
| 管理画面からのファイル編集（DISALLOW_FILE_EDIT） | 無効化されていなければ改善を提案 |
| 管理者ユーザー名が admin か | 既定名のままなら attention |
| 常時HTTPS（SSL）か | 非SSLなら recommended |
| データベース接頭辞が wp_ のままか | 既定のままなら軽い注意 |
| XML-RPC の有効状態 | 有効かつ未使用が疑われる場合に情報提示 |
| REST APIのユーザー名列挙の可否 | 列挙可能なら注意 |

### カテゴリC：衛生状態

| 項目 | 判定の考え方 |
|---|---|
| 無効化されたまま放置のプラグイン・テーマ | 検知して削除候補として提示（削除は手動） |
| 既知の対策系プラグインの導入有無 | 入っていなければ選択肢として情報提示（誘導はしない） |

合計でおおむね12項目前後に収めます。これ以上増やすと診断が重くなり、軽量という強みを自分で損ねます。MVPとしてはカテゴリAとBを優先実装し、Cは後追いで構いません。

---

## 4. 三段階の表示ルール（既存パターンの踏襲）

| 状態 | 意味 | トーン |
|---|---|---|
| good | 問題なし | 緑・安心させる |
| attention | 改善が望ましい | 黄・急がせない |
| recommended | 早めの対処を推奨 | 赤寄り・ただし煽らない |

平易さの方針に従い、各項目には「なぜ問題か」を一文、「どうすればよいか」を一手順だけ添えます。専門用語が必要なときは、かっこ書きで噛み砕いた説明を入れます。自動修正は行わず、ボタンで設定画面へ案内する程度にとどめます。

---

## 5. スコープ外（無料に入れないもの）と理由

| 機能 | 扱い | 理由 |
|---|---|---|
| CVE脆弱性アラート | Pro | 外部DB突合が必要。有料の目玉として温存 |
| プラグイン更新の実行代行＋更新前の自動バックアップ | Pro | 「壊れても戻せる」を保証して初めて代行に価値が出る。無料は標準更新画面への案内まで |
| 定期自動チェック＋メール通知 | Pro | 常駐処理・配信基盤が必要 |
| マルウェアスキャン | 作らない | 重く、軽量方針に反する |
| 自前WAF | 作らない | 同上。大手と機能量で戦わない |
| ログイン試行制限などの対策機能 | 作らない | 常駐処理・自動介入になり方針に反する。導入有無の診断にとどめる |

無料版でできることを意図的に「診断まで」で止めることが、Proへの自然な動機づけになります。危険を見つけたら、その危険度を詳しく知るのがPro、という導線です。

---

## 6. 実装の優先順位（MVP）

1. カテゴリBのハードニング設定（既存のデバッグ診断に項目を追加する形で拡張しやすい）
2. カテゴリAのバージョン鮮度（WordPress組み込み情報の読み取り）
3. カテゴリCの衛生状態
4. 三段階表示のメッセージ文面整備（平易な日本語のテンプレート化）

まずカテゴリBを既存実装の延長で固め、公式リポジトリ申請に必要な最小構成を最短で作るのが、フェーズ0を早く抜ける近道です。

> 各項目の判定しきい値・表示文面・コード実装（接頭辞やフックの扱い）は、本書では確定させず要件レベルにとどめます。実装は既存リポジトリの構造を確認しながら個別に決定します。

---

## 7. 次のアクション

1. カテゴリBの各項目について、good / attention / recommended の判定しきい値を確定する
2. 各項目の表示文面（なぜ問題か・どうすべきか）の日本語テンプレートを作る
3. 公式リポジトリ申請に必要な項目数の最小ラインを決め、フェーズ0の完成定義とする
